# Releases and publishing

Hibi uses GPL-3.0-only. Packaged applications include the root `LICENSE.md`.

## Beta and nightly builds

Hibi has two update channels: **Beta (stable)** is the default, and **Nightly (bleeding edge)** follows every published build, including betas. Back up your notes before installing a nightly. The [release policy](../../development/core/releases.md) is maintained in `hibigarden/docs`.

The `nightly and releases` workflow runs on `main` daily at 18:00 UTC (02:00 Manila time), subject to GitHub scheduling delays. Manual runs accept `bump: patch` (the default) or `bump: minor`. Manual runs also accept an exact plain-semver `version` and a `force_release` boolean. A trailing `^` on `version` enables force and is stripped before creating the tag. Existing version tags are rejected. Scheduled runs ignore these inputs and always use patch. The `clean` option bypasses download caches; compilation and the full required checks run either way. Version tags do not trigger releases. The `releases` concurrency group serializes the entire workflow so version selection cannot race another release run.

The workflow fixes one source commit and passes through five stages:

1. **Prepare** finds the numerically highest plain `v<semver>` tag and computes the next patch version, or the next minor `.0` for a manual minor bump. The plain version in `package.json` is a floor. With a floor of `0.2.0`, the first beta is `v0.2.0`; after `v0.2.9`, patch produces `v0.2.10` and minor produces `v0.3.0`. It also prepares a dated nightly identity and a commit changelog.
2. **Checks** run the full required suite in four isolated shards on each of five platforms. Every shard records its platform, source commit, shard number, and result. Missing, duplicate, or mismatched reports stop the release.
3. **Decide** aggregates all 20 shard reports and outputs `channel`, `tag`, and `version`. Every check must pass for a beta, and HEAD must contain commits since the latest version tag. An unchanged HEAD or any failed, skipped, or cancelled check selects a nightly. A requested version can release an unchanged revision after passing checks. Explicit force selects a beta even with failed checks, retaining every recorded result; missing, duplicate, and mismatched check reports still stop publication.
4. **Build** compiles and packages each platform with that decided version. The version is embedded before signing. Always-run package reports record the source commit, channel, tag, version, build result, checks, package result, existing platform verification, and job result. Build jobs may fail independently. Only complete installer sets from successful, verified platforms are uploaded.
5. **Publish** independently reads all shard reports again and compares the decision with every package report. Identity mismatches and duplicate reports refuse publication. Failed or missing platforms remain in the report but contribute no installers. One shared allowlist filters Actions artifacts, release attachments, notes, webhooks, and updater inputs. Empty builds produce a metadata-only release without installer links. A beta becomes a full GitHub release marked latest; a nightly remains a prerelease with `latest=false`. An existing published immutable release keeps its assets and feeds and is not announced again. A same-SHA draft can retry interrupted uploads or finalization: stale attachments are pruned and only current verified files are replaced.

Platforms and installers are:

- Linux x64 and native Linux arm64 (`ubuntu-24.04-arm`): AppImage, Debian package, and Flatpak bundle.
- Windows x64: NSIS installer.
- macOS Apple Silicon and Intel: signed, notarized DMG and ZIP.

Nightlies use tag `nightly-<yyyy-mm-dd>-<sha7>-<run>-<attempt>` and version `<next-beta-base>-nightly.<yyyymmdd>.g<sha7>.<run>.<attempt>`. For example, after `v0.2.0`, a nightly can be `0.2.1-nightly.20261025.gabcdef0.12.2`. Check failures do not change this format. Unchanged revisions still receive a new nightly. Failed checks remain visible as a failed workflow after automatic nightly publication and notification. Explicit force records them as warnings rather than failing the run. Compilation, packaging, or verification failure excludes that platform without blocking other platforms or publication.

Each immutable release contains installers, `SHA256SUMS.txt`, `release.json`, `feed.json`, and the `latest*.yml` metadata used by electron-updater. Notes contain per-platform check and package results, the logs link, downloads, checksums, and commits since the previous reachable dated or versioned release. Rolling channel tags are excluded from changelog baselines. The first release includes all history when no earlier release exists. Failed uploads leave a draft for retry; temporary Actions artifacts expire after one day.

## Update feeds and the bridge

The rolling `beta` and `nightly` releases are prereleases with `latest=false`. They carry `feed.json` at `releases/download/beta/feed.json` and `releases/download/nightly/feed.json`. A beta advances both channel listings; a nightly advances only nightly. Complete builds update their automatic feeds too. Partial and metadata-only publications update the listings with available downloads and an explicit feed notice, while preserving existing `feed.json` assets. A first partial publication creates the listing without a feed. Beta promotion checks that the old rolling commit is an ancestor of the new commit and preserves the previous feed otherwise. Installers remain on immutable releases; rolling releases do not mirror them.

The feed contains `tag`, `version`, and `assets`. Shipped readers require every filename to match that single version, download all packages from that single tag, and require both macOS ZIPs. Mixing old and new platform versions would be invalid, so partial builds preserve the entire last-complete rolling feed. Per-platform advancement requires a compatible reader/schema change. Each platform asset has `name`, `sha512`, and `size`; macOS assets also include a `zip` object with those fields. Windows NSIS, Linux AppImage, and macOS ZIP updates use electron-updater. Debian and Flatpak packages remain manual downloads. Linux architecture aliases are normalized to `linux-x64` and `linux-arm64`, and conflicting names stop publication. The immutable release keeps `latest.yml`, `latest-linux.yml`, `latest-linux-arm64.yml`, and `latest-mac.yml` with hashes matching the feed.

The main process fetches the chosen channel's `feed.json`, validates the immutable tag/version pair and installer names, and pins downloads to that release. Beta accepts only a `v<semver>` tag with the matching plain version. Nightly also accepts dated nightly entries. Update ordering compares the version core first, then puts a plain release above its prereleases, then orders nightlies by date and numeric run/attempt rather than commit hash. Existing preferences migrate once on read: `nightly-green` becomes `beta`, `nightly` stays `nightly`, and missing or invalid values become `beta`. Download verification, restart confirmation, and unsaved-document handling remain in the main process.

The rollout requires two merged changes in order. First ship the updater bridge with package floor `0.2.0` while retaining the old workflow and scripts. Run that old workflow once to publish an all-platform passing `0.2.0-nightly.<date>.g<sha7>.<run>.<attempt>` build through the existing feeds. That build can be accepted by old installed updaters and contains the new updater. After the workflow change merges, the beta feed can deliver `v0.2.0` to bridged apps. The legacy `nightly-green/update.json`, `nightly-green/recommended-nightly.json`, and `nightly/update.json` remain frozen at the bridge. The new workflow never writes them.

## Signing, notifications, and validation

Packages use `com.ryanaque.hibi`, the icons in `electron-builder.yml`, and the regular app's data profile. Windows packages are unsigned. macOS packages use Developer ID signing and notarization; signed ZIP metadata supports in-app replacement. `npm run dist` runs the complete checks before creating local installers. Release builds use download caches only; cached builds and previous test results never certify a release.

Only the publish job has `contents: write`; publication needs no extra token. Set `NIGHTLIES_WEBHOOK_URL` to enable Discord announcements after successful immutable publication and feed updates. Both mention role `1550309423166267432` and use the butterfly embed. Betas use color `9568176` and state that every platform passed its checks, except forced releases explicitly disclose the override and refer to the recorded results. Nightlies use neutral color `9807270` and remind readers to back up because they are bleeding edge and may be broken. Both include the source commit and direct installer links. The request uses an explicit mention allowlist, `wait=true`, and a 30-second timeout. An unset secret skips delivery. Notification failures do not undo publication.

For workflow-only edits, run `node --test --test-concurrency=1 tests/nightly.test.mjs tests/update-feed.test.mjs` without building Electron. These cover forced release inputs, provenance, partial and zero artifacts, draft retries, notifications, and channel preservation. For updater application changes, also run `tests/updates.test.mjs` after building the app. The updater file includes the focused Electron settings test; run only one Electron suite at a time. Check workflow syntax with `actionlint .github/workflows/nightly.yml`.

## Website addon catalog

`.github/workflows/addons-sync.yml` runs when a push to `main` changes `src/addons/**`, or on manual dispatch. `node scripts/export-addons.mjs` copies `authors.ts`, manifests, Markdown, and images into `out/addons`, preserving relative paths. It excludes runtime TypeScript, CSS, audio, hidden files, and symlinks. Legacy manifests are copied without execution. For JSON packages, the exporter validates `hibi-addon.json` with the shared compiled-manifest parser and generates a `manifest.ts` object literal for the site's static reader. The JSON remains the only maintained metadata; its compatibility shim is not copied. The workflow installs dependencies without lifecycle scripts before validation, and the exporter never executes addon code.

The workflow replaces generated catalog files in `hibigarden/site/addons`, removes stale files, and preserves `addons/index.html`. After the site's tests and build pass, it commits `chore(addons): sync to main (<source short commit id>)`. Unchanged data creates no commit. Runs are serialized and use normal pushes, preserving concurrent site work.

Set `ADDONS_SYNC_TOKEN` in **schmayterling/hibi**, with access to `hibigarden/site` and Contents read/write permission. The source workflow cannot read a secret stored in the destination repository.

Documentation publishes separately through `docs-sync.yml`, only when `docs/**` changes on `main`. See [documentation publishing](validation.md#documentation-publishing) for setup.
