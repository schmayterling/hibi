# Startup and shutdown investigations

Tracks [#251](https://github.com/schmayterling/hibi/issues/251), [#252](https://github.com/schmayterling/hibi/issues/252), and the unresolved cursor case in [#64](https://github.com/schmayterling/hibi/issues/64).

The Windows startup reports in #251 predate this change. They do not establish that asset delivery, static imports, renderer scheduling, and background activation share a cause. Keep the original #234, #235, and #239 evidence linked from that issue. Injected failures exercise diagnostic coverage; they do not reproduce those Windows incidents.

Preload uses Electron's contextBridge.executeInMainWorld to register error and unhandled-rejection listeners before the desktop entry script, document-transfer hydration, and application imports. Isolated-world listeners do not receive these page errors; only location primitives cross back to preload for catalog validation. RENDERER_PRE_ENTRY marks observer installation, and RENDERER_STARTUP_FAILED records an observed pre-entry failure without suppressing its native propagation. If this experimental bridge operation throws, only pre-entry observation is lost: the normal renderer diagnostic bridge still starts. The renderer takes over only after its own listeners are installed; its stack projection and diagnostic metadata load on the first failure, outside the unchanged startup byte budget. The local log distinguishes pre-entry errors from background activation failures.

Navigation and stalled/failed core asset records identify only build-owned artifact numbers, status codes, and bounded elapsed times. A canceled load (Chromium ERR_ABORTED, code -3), including a navigation superseded by another load, produces informational NAVIGATION_ABORTED rather than critical NAVIGATION_FAILED. Other main-frame load failures remain critical; subframe failures do not produce these navigation records. Whenever main treats a startup load failure as fatal and shows the could-not-start dialog, it records critical MAIN_STARTUP_FAILED itself, so a packaged build's aborted startup load is never only informational. Artifact 8 identifies the app entry document; match JavaScript artifact numbers against the same build's diagnostic-artifacts.json. Local logs never contain requested URLs, addon names, error messages, or document paths. Native exits retain Electron's reason and exit code with an explicit unavailable-native stack status.

Startup fault tests clear Playwright's page-error buffer before injecting a failure and subscribe to pageerror before navigation. Wait for both the original browser error and the local diagnostic record: they travel through different transports. A repeated rejection probe captured an empty snapshot whose original error appeared in the unfiltered buffer 100 ms later; selecting all errors alone does not remove that ordering race. Failure snapshots use page.pageErrors({ filter: 'all' }); the default hides errors preceding the latest main-frame document navigation, so a later navigation must not erase the original failure from the snapshot. Keep the original message, generated-file stack, and missing renderer-entry assertions. These harness checks do not identify the cause of the historical Windows incidents.

The custom-word database has its own worker and is separate from Chromium's BtmStorage/BtmDatabase. Graceful dictionary shutdown drains admitted requests, asks the worker to close SQLite, and waits for worker exit before recording SQLITE_CLOSED. The tests also exercise profiles using WAL mode; the dictionary does not change an existing profile's journal mode. A 1.5 second timer records SQLITE_CLOSE_WAITING but does not terminate the worker or treat the close as completed.

A close error records SQLITE_CLOSE_FAILED and retains the worker. The next open or stop retries that close before creating replacement stores; concurrent opens share the retry, and another disable invalidates waiting opens. A repeated failure rejects the request while preserving the worker for another attempt. Open-driven retries back off: for one second after a failure, doubling up to thirty seconds, further opens reject with the retained error without sending another close; stop and quit always attempt the close, and a successful close resets the schedule. Committed words remain durable. Disabling the dictionary waits only for the generic two-second addon deadline; its close keeps running, and the next open waits for completion. Quit has no dictionary close deadline, because process exit would abandon a still-running SQLite close. An actual close error never cancels quit: will-quit runs after every window has closed, so the handler resumes quitting on both success and error. Never delete WAL/SHM files or force a checkpoint to work around this wait.

SQLite documents that the last connection normally checkpoints and removes its WAL on close, and that the WAL is persistent database state:
https://sqlite.org/wal.html
https://sqlite.org/c3ref/close.html

The Electron 44.7 native sample in #252 concerns Chromium storage during TaskTracker::CompleteShutdown. This repository change cannot certify that upstream wait as fixed. Electron's supported session.flushStorageData() flushes DOMStorage; it is not a BtmDatabase close API:
https://www.electronjs.org/docs/latest/api/session
