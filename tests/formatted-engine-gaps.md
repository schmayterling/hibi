# formatted engine product gaps

these todos execute their assertions. each row identifies a reproduced parity gap, its annotation, and the owning product work. the product fix must remove the todo and this row, then rerun the complete native file. setup failures and flakes do not belong here.

owner numbers follow the ordered formatted engine readiness plan. the default flip requires `HIBI_EXPECT_FORMATTED_GAPS=0 node --test tests/formatted-engine-gaps.test.mjs` to pass. the count is annotation count; a shared annotation can execute in more than one fixture. locations identify the todo option or literal map entry to remove.

accepted differences are not gaps; their tests assert each engine. the codemirror side-by-side formatted pane stays editable, with its caret and the markers under it, while the rich editor previews read-only. after a code language is turned off and on while source mode hides the formatted view, the rich editor refreshes its highlighting once when shown; codemirror leaves the unchanged view as it is, and its shown highlighting follows the language.

## accepted differences

api-004: typing context uses opaque editor-local positions in API 1, 2, and 3. `editor: 'rich'` does not identify the implementation. Legacy rich view retains ProseMirror positions, including node boundaries; CodeMirror source and formatted views use normalized-source UTF-16 offsets. Replacing `chosen` in `before chosen after 😀` reports 8..14 in ProseMirror and 7..13 in CodeMirror. Both must report the live committed selection and matching nearby text, with `change.from + change.insertedLength === selection.head`. The complete formatted-completions file verifies both implementations and CodeMirror CRLF normalization.

API 1/2 and the public docs promised ProseMirror numbering for `rich`; this difference is accepted because no known addon depends on it. The API 2 declaration at `8bd8d8bda86d54cbd3fc0ad6a004ec83c69d71f8` distinguished CodeMirror and ProseMirror positions. The pinned public guide at docs revision `de79e8e0fb6066a155a96482f690e3a543239b46`, `development/addons/adding-functionality.md:74`, still says ProseMirror positions in rich view. Update that page in hibigarden/docs and bump the pinned revision before changing the default engine. The addon starter uses no positions. The published catalog's five extensions (fatass-horse, fnaf-jumpscare, oneko, typing-speed, and hibi-doom at `446296f572ba80ba6290fba864f104412794bca2`) use no selection/completion position APIs; its six themes use no editor positions. Bundled autocomplete compares changes with captured selections, and writing-suggestions derives ranges from selection.head; neither requires ProseMirror numbering.

corpus-004, corpus-014: a reference in a `-# ` subtext line resolves against a definition later in the note in the formatted view ([markdown-semantics-native.test.mjs:118](markdown-semantics-native.test.mjs#L118), [markdown-semantics-native.test.mjs:119](markdown-semantics-native.test.mjs#L119)). The native schema reads subtext text before later definitions exist, so the rich view, export and word count leave it literal. Each engine asserts its own outcome; word count and export keep the native reading.

marker-005: copying from the formatted view puts the selection's exact Markdown on the clipboard as text, as a Markdown editor does, and its rendered HTML as HTML ([markdown-markers.test.mjs:867](markdown-markers.test.mjs#L867)). The rich editor copies rendered text. A formatted-view copy pastes back as the same Markdown; formatted-clipboard.test.mjs covers that contract.

marker-007: with markers shown, the formatted view reveals a focused heading's `# ` as editable text, so the heading's text content includes it; the heading's name in the accessibility tree is the rendered heading text ([sidebar-views.test.mjs:103](sidebar-views.test.mjs#L103)). The rich editor draws the marker as generated content outside the text. Each engine asserts its own outcome.

find-002: with the find bar open, undoing an edit that replaced the selected match restores that selection in the formatted view, so the restored match is the current one (1/10000), as in source view; the find count reflects the selection it is given ([formatted-find.test.mjs:531](formatted-find.test.mjs#L531)). The rich editor leaves a caret after the restored text, so it shows 0/10000. After closing the bar, typing and undoing, reopening it searches again from the selection, and both engines show the first match as current (1/10000).

input-071: in a table cell the formatted view keeps small text, headings, lists, quote, code block, divider and table disabled ([editor-input.test.mjs:3565](editor-input.test.mjs#L3565)). The rich toolbar enables them, but a cell holds only inline Markdown, so it writes each as literal cell text, and reopening the note reads it back as text: `# cell`, `- cell`, `1. cell`, `- \[ \] cell`, `&gt; cell`, inline code `` `<br>cell<br>` ``, the text `---` between line breaks, or two line breaks in place of a table. The frozen rich record stays as captured. The line break action is parity in both engines and writes `<br>`.

toolbar-001: a range with a block outside every list, or quote, of one kind does not show that action as active in the formatted view ([formatted-toolbar-state.test.mjs:913](formatted-toolbar-state.test.mjs#L913)). The rich editor sums the positions each such node covers, so nested lists count twice and a range from a nested item into the paragraph after the list can report the list, as in `- itemA\n- i[temB\n  - itemC\n\npla]inD`. The formatted view stops reading a range once every action's state is known, and a block outside the kind decides it. The quote action follows from it: on such a range the rich editor's toggle tries to lift the double-counted quote and refuses, while the formatted view's action quotes the selected blocks, which join the quote around the range's start (`> quoteA\n>\n> > quoteB\n>\n> quoteC\n\nplainD` from `quoteB` to `plainD` keeps quoteB nested and brings plainD into the outer quote). List actions keep the rich editor's enabled states.

input-041: replacing `b`…`c` in `ab` / `## cd` with typed `X\nY` keeps the joined `Yd` plain in the formatted view (`aX\n\nYd`, [editor-input.test.mjs:2667](editor-input.test.mjs#L2667)). the rich editor makes it bold: chromium copies the heading's theme style onto the joined text (`<span style="font-size: 24px; font-weight: 600; letter-spacing: -0.02em; caret-color: transparent;">Yd</span>`) and the rich editor reads the weight as bold. with default styles chromium leaves `Yd` plain. evidence: electron 45 (chromium 156), `page.keyboard.insertText` into the rich editor's DOM with its input handler off and its DOM observer paused, and into a plain `contenteditable`.

input-042, input-048: after typed multi-line text, the formatted view puts the caret after the last typed line (`Y|d` for block kinds, `b|` for a task; [editor-input.test.mjs:2666](editor-input.test.mjs#L2666)). the rich editor leaves it before that line (`|Yd`, `|b`). chromium's own multi-line input leaves the caret early even in a plain paragraph: `start|END` with `a\n\nb` leaves it in the empty middle paragraph. the rich editor's handler moves the caret after the input in every case it handles; these two are cases it leaves to the browser.

input-049: typed `a\n\nb` at the end of `y` in `- x` / `  - y` keeps `ya` nested in the formatted view and outdents the new item, as its Enter does (`- x\n  - ya\n- b`, [editor-input.test.mjs:2669](editor-input.test.mjs#L2669)). the rich editor gives `- x\n- ya\n- b`. chromium outdents the emptied item by moving the nested list out of its item (`<ul><li><p>x</p></li><ul><li><p>ya</p></li></ul><li>b</li></ul>`, which still shows `ya` nested), and the rich editor's parser flattens that invalid nesting.

multi-line input in the middle of a task item: the formatted view makes each typed line after the first a new unchecked task, as Enter makes it (`- [x] abx\n- [ ] \n- [ ] ycd` for `x\n\ny` at `ab|cd`, [formatted-commands.test.mjs:888](formatted-commands.test.mjs#L888)). the rich editor makes the first new line a task and nests every later line under it as a bullet, empty lines included, so the same lines become siblings or nested bullets depending on how many are typed: `x\ny\nz` gives `- [ ] y` with `  - zcd` under it. that comes from the browser's edit of the task DOM (the item it adds has no checkbox wrapper, and later lines go inside it), read back by the rich editor's parser. at the end of an item both leave the list at an empty added task. evidence: handler-off rich editor results for `x\ny`, `x\n\ny`, `x\ny\nz`, `x\ny\nz\nw`, `\n\n` and `x\n\n\ny` after `ab` in `- [x] abcd`. the formatted and native app outcomes for `x\n\ny` both execute in [formatted-multiline-regressions.test.mjs:114](formatted-multiline-regressions.test.mjs#L114) and [formatted-multiline-regressions.test.mjs:191](formatted-multiline-regressions.test.mjs#L191).

open-001: a note that ends in a block the rich editor draws as one node (an HTML block or comment, a math, Mermaid or Typst block, a divider, an image) opens with that block node-selected there, and with its source selected whole in the formatted view, which does not show the source of a selection it opened with ([formatted-open-caret.test.mjs:87](formatted-open-caret.test.mjs#L87)). Typing replaces the block in both, and Enter adds a paragraph after it ([formatted-open-caret.test.mjs:291](formatted-open-caret.test.mjs#L291)). Backspace or Delete then leaves an empty paragraph where the block was in the formatted view (`plain\n\n\n`); the rich editor removes the block and its paragraph (`plain\n`). The rich editor's selected divider takes no typing, Backspace, Delete or Enter, while the formatted view's replaces, deletes or follows it like the other blocks. Everywhere else a note opens with the caret where the rich editor's `Selection.atEnd` puts it, the end of the last text block's text through quotes and lists, in a table's last cell and before a closing fence; the same file asserts that parity for each kind.

open-002: a table whose last row has fewer cells than columns opens in the rich editor's padded empty last cell, and in the formatted view at the end of the row's last written cell ([formatted-open-caret.test.mjs:100](formatted-open-caret.test.mjs#L100)). The source has no text for the missing cell, so no position opens it.

open-003: the rich editor's indented code block keeps the source's last line break, so a note ending in one opens on an empty code line the source does not have; the formatted view opens at the end of the code's last line ([formatted-open-caret.test.mjs:104](formatted-open-caret.test.mjs#L104)). An empty fenced block shows an empty code line in the rich editor, which holds the caret, while the formatted view draws no lines for it and the caret rests after it ([formatted-open-caret.test.mjs:108](formatted-open-caret.test.mjs#L108)).

open-004: a note whose end is not parsed by the formatted view's first paint opens with the caret at the end of its text ([formatted-open-caret.test.mjs:113](formatted-open-caret.test.mjs#L113)); the rich editor opens it where its `Selection.atEnd` puts it. Opening never parses the rest of a long note. Once the parse reaches the end, as when the note is scrolled there, or a renderer that draws its last block loads, the formatted view moves the selection where the rich editor puts it, unless the user moved it or edited first ([formatted-open-caret.test.mjs:334](formatted-open-caret.test.mjs#L334)). A note the rich editor opens beside its source, such as one with footnotes, has no rich caret to match.

table-pick-001: with the selection's anchor in a table cell, a shift-press on another table's cell text extends the selection there in the formatted view, and a drag from it takes the head through that table's cells, as a shift-press or shift-drag outside the tables does ([formatted-tables.test.mjs:850](formatted-tables.test.mjs#L850)). The rich editor's cell selection cannot span two tables: it puts a cell selection on the anchor's cell and ignores the drag; pressed on the other cell's padding instead, it keeps its caret. Each engine asserts its own outcome.

triple-001: a triple-click on a block the rich editor draws as one node (an HTML block or comment, a divider, an image, a math, Mermaid or Typst block) selects the block's source in the formatted view, without the line break after it, so typed text replaces the block as over the rich editor's node selection ([formatted-view.test.mjs:1118](formatted-view.test.mjs#L1118)); images, formulas and rendered fences do so when the press is on their drawing, and a press on a fence's shown source selects its code. The formatted view has no node selection: while markers show, a selection in one block shows its source, as anywhere. Each engine asserts its own selection and the same note after typing over it, except for a divider: the rich editor takes no typed text or Backspace over a selected rule, while the formatted view replaces or deletes its source. Backspace over a selected HTML block leaves the blank lines around it in the formatted view, which the rich editor's serializer joins. A single click places the caret beside the block in the formatted view; the rich editor node-selects it.

shift-word-001: shift-double-click extends the selection to the far edge of the clicked word in the formatted view, as CodeMirror does, from a cell too ([formatted-tables.test.mjs:606](formatted-tables.test.mjs#L606), [formatted-tables.test.mjs:557](formatted-tables.test.mjs#L557)). The rich editor extends it to the click, as a shift-click does, in plain text and from cells. Matching it would change the shared drag loop in formatted/tables.ts; each engine asserts its own outcome.
